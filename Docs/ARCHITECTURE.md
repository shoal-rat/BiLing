# 知音的结构

> 名词见 [WORLD.md](WORLD.md)。这里讲每一部分为什么是现在这个样子。

```
按键 ──► 弦 KeyReader ──┬──► 琴谱 Qinpu（词典，CPU，毫秒级）──────────┐
         三条读法 + 走音 │                                              ├──► Composer ──► 候选窗「弦」
                         └──► 子期 Ziqi（GPU，约 30–60 ms）            │        ▲
                               ├─ 听音：基座 + LoRA，看得见按键         │        │
                               └─ 知意：原始基座，只看前文              │     默契 Moqi
                                  两耳逐 token 共同打分，受「弦」约束 ──┘   （本机加密学习）
```

## 1. 弦：一套读键规则，三处共用

一个字从按键位置 p 能读到哪里，只有四种方式：

1. **全拼** `zhong`；
2. **声母**（zh/ch/sh 可一可二）`z` `zh`——只在这个字的任何读音都没有被全拼拼出时才允许，所以 `dan` 永远不会被读成 大+安，而 `dg` 是 大哥；
3. **前缀**，只在按键末尾：正在敲的那个音节 `zho`；
4. **走音**（手误）：相邻键、两字母颠倒、漏一个、多一个字母，带代价，一次输入最多两处。只有按键*不能*整齐地读成完整音节时才启用，所以正常打字不为它付一分钱。

这套规则同时写在 Python（`Tools/zhuoqin/pinyin.py`，生成训练数据）和 Swift（`Sources/ZhiyinCore/Strings/KeyReader.swift`，运行时），由测试钉住。训练数据只包含规则能读回的按键，解码器只考虑规则允许的 token——两边一旦不一致，模型学到的东西就用不上。

多音字只保留真正被用到的读音（`Resources/Data/char_readings.json`，由万象词库加权统计）：pypinyin 认为 洋 也读 xiang，于是旧方案会把 xiangqi 解成 洋气。

## 2. 琴谱：零启动开销的词典

42 万词（万象 + Rime pinyin-simp，词频用我们自己语料重估，异常词条被压平），编译成一个字符 trie 文件，**直接 mmap，启动零解析**。查词就是用「弦」的规则沿 trie 走：根节点按音节建索引，只访问读得通的子树。在此之上做 k-best Viterbi，给出整句候选和"取前几个字"的候选。只收简体字。

琴谱的角色：

- 子期还没回话的那几十毫秒里，先给出一个能用的列表；
- 子期休息（闲置释放、低电量、关闭）时独奏；
- 提供长输入"先选前面一个词"的候选。

## 3. 子期：两只耳朵

这是本次重构的核心，也是踩坑最多的地方。

**第一版（失败）：只用微调模型。** 把 Qwen3-0.6B-Base 用 LoRA 微调成"读前文 + 读按键 → 写汉字"。每个按键是一个单字母 token，敲一个键只追加一个 token，KV 缓存全复用。问题是：在这台 M5 上能负担的训练量（几百万 token）下，模型学会了"对齐"（哪几个字母是一个音节），却**丢掉了语言感**：`jiangjinxingshengwufangyuyanxi` 给出 将进行省务房与演戏。教师强制打分显示，模型本身就更偏爱单字 token。

**第二版（意外地好）：只用原始基座，不给它看按键。** 按键只用来约束可选 token，再加一个打字信道模型（声母读法要付代价，部分假设按"已读的键数"折算）。没有任何训练，准确率就超过了第一版——基座模型的语言知识是完整的。弱点是缩写：看不见后面的键，`zggcy` 不知道该往 中国工程院 走。

**最终版：两只耳朵一起听（product of experts）。**

| 耳 | 模型 | 看见什么 | 擅长 |
|---|---|---|---|
| 听音 | 基座 + LoRA 适配器（81 MB） | 前文 + 全部按键 | 对齐、缩写、正在敲的半个音节、走音 |
| 知意 | 原始基座 | 只有前文 | 什么样的中文是通顺的 |

每一步、每个候选 token 的分数 = w₁·log P听音 + w₂·log P知意 − 信道代价。两个上下文共享同一份模型权重（mmap 一次），各自缓存前缀，在两个线程里并行 decode。

**约束解码。** 每一步只考虑「弦」允许的 token（模型词表里 2.26 万个纯简体汉字 token 组成的 trie，外加大写单字母和英文 token），所以子期只能"选"，不能"编"。搜索是 token 同步的束搜索：所有活假设输出长度相同，作为一批单 token 序列一次送进 GPU，共享前缀的 KV 单元；分叉时只复制序列标记，不复制数据。

**每个按键的代价。** 听音的提示词每敲一个键追加一个 token；知意的提示词（只有前文）在整个组合过程中完全不变。新按键到来时，旧搜索在下一步之间被取消（代次标记），浪费最多一步。

## 4. 能耗策略

- 模型只在你按键时工作；没有任何定时轮询。
- 闲置 15 分钟（可调）释放模型；下一个键唤醒，约 0.5 秒。
- 候选窗只在子期"正在听"时让弦轻颤（最多约一秒），其余时间一像素不动。
- 「轻听」把束宽从 10 降到 5；低电量模式默认独奏（只用琴谱）。
- 用 Q4_K_M 量化基座（372 MB），LoRA 适配器单独加载，不再多存一份模型。

## 5. 默契

记住"哪串键你选了哪个词"，三周半衰期。子期不强烈反对时（分差 < 4 nat）把你选过的词提到第一；子期从来不会说的（人名、自造词）直接插入候选。AES-GCM 加密，密钥在钥匙串，目录不进 Time Machine。密码框（Secure Input）、网址、邮箱、长数字从不学习。

## 6. 斫琴：训练流水线

`Tools/zhuoqin/`：

| 步骤 | 脚本 |
|---|---|
| 读音表 | `build_readings.py` |
| 训练样本（前文、按键、目标） | `make_dataset.py`（打字模拟：全拼/混合/声母/半个音节/走音） |
| 新词包 | `make_xinci.py` + `xinci/*.txt` |
| 训练 | `train.py`（MLX LoRA，只在目标位置算 LM head——否则 15 万词表的 logits 会吃掉几十 GB） |
| 参考解码器 | `beam.py`（与 Swift 版逐项对齐） |
| 导出 | `export_lora.py`（MLX LoRA → PEFT → GGUF 适配器） |
| 词典 / 词表 trie | `build_tries.py` |
